# 项目文档与发布闭环

## 工作顺序

1. 用 Keeper 确认工程身份、定位代码，阅读 [架构](../docs/项目架构.md) 或 [构建](../docs/构建发布.md)。
2. 实现与验证；用 `python -X utf8 .codex/项目管家/keeper.py affected` 计算相对上次成功发布的受影响文档（包括新增、修改、删除）。
3. 管家对每份受影响文档做语义判断：职责、入口、契约或验证方法是否改变。改变则更新原文；没有改变则保持原文，在交付中说明。新增稳定模块时同时加入 `doc-map.json`。
4. 执行 `Build.bat`，按需使用用户指定的 `--version X.Y.Z`。入口会检查文档、运行测试、发布 Lite 和 Portable、验证包内容并刷新 Keeper。
5. 查看退出码和 `Build/latest.json`，再交付程序路径、版本、验证结果及实际未覆盖范围。

## 文档分工

- [AGENTS](../AGENTS.md)：工作规则。
- [管家自述](项目管家/管家自述.md)：身份与工具使用。
- [项目架构](../docs/项目架构.md)：代码现状与稳定契约。
- [构建发布](../docs/构建发布.md)：版本、输出、失败恢复。
- [HOOKS](HOOKS.md)：触发方式、信任要求、日志与防重复。
- `docs/VALIDATION*.md`：特定时期的验收证据，保留其历史版本和限制，不批量改写版本号。既有任务修改报告与本轮构建结果分别看待。

## 自动化边界

`doc-map.json` 声明文档、负责的代码前缀及真实入口。校验要求“职责、入口、契约、验证”四个章节以及入口文件存在；不证明文档语义正确。所有非忽略文件进入变更哈希（排除运行数据、缓存和生成物），因此 Shell 写入、未跟踪文件与删除也能被发现，无需依赖编辑工具事件。

本项目规模小，Stop 时统一检查，不在每次工具调用后扫描全仓库或发布半成品。机器索引增量更新文件文本，不解析 C# 语义调用关系。无新增改动时不重复发布；发布成功后才推进基线，失败仍留待完成。
